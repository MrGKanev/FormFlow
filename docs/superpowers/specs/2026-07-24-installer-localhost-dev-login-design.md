# First-run installer, localhost dev-login, and shared admin/homepage styling - design

Date: 2026-07-24
Status: draft (pending user approval)

## Purpose

Three requested pieces:

1. Hide the `/admin` link from the public homepage unless the visitor is on
   localhost, and add a one-click "log in as admin" button on the login page
   that's only usable from localhost (no username/password typed).
2. A first-run web installer at `/install` that writes `.env` when it's
   missing, and permanently refuses to run again once `.env` exists.
3. A basic shared visual design (light, clean, utilitarian, with a dark-mode
   variant via `prefers-color-scheme`) applied consistently to the homepage
   and every admin page, replacing today's unstyled tables and the
   dark/monospace homepage.

## 1. Localhost-only admin link + dev-login button

**Homepage** (`public/index.php`): compute
`$isLocalhost = in_array($_SERVER['REMOTE_ADDR'] ?? '', ['127.0.0.1', '::1'], true)`
and only emit the "Admin panel" link when true. The `/health` link stays
always visible.

**Login page bypass**: `AdminController` gains a private
`isLocalRequest(): bool` helper (same loopback check). `renderLogin()`
passes `isLocal` to the `login` view. When true, the view renders a second
small form alongside the normal one:

```html
<form method="POST" action="/admin/login">
  <input type="hidden" name="csrf_token" value="...">
  <input type="hidden" name="dev_bypass" value="1">
  <button type="submit">Log in (localhost)</button>
</form>
```

In `handleLogin()`, after the CSRF check, if `$_POST['dev_bypass']` is set
**and** `isLocalRequest()` is true server-side (the POST body is never
trusted alone - this is re-checked against `REMOTE_ADDR`, same as the view
gate), skip the rate limiter and `password_verify()` entirely, call
`session_regenerate_id(true)` + `$this->auth->login()`, and redirect to
`/admin`. Any other case falls through to the existing username/password
path unchanged.

This does **not** bypass the IP whitelist gate that already runs before the
login page is reachable at all - an operator still needs `127.0.0.1`/`::1`
in `config/admin.php['allowed_ips']` (or the dynamic whitelist) for local
testing, exactly as documented today. The bypass only removes the
credential-typing step once you're already there.

## 2. First-run installer at `/install`

**Routing** (`public/index.php`, checked right after parsing `$path`):

- `$envExists = is_file($root . '/.env')`.
- If `$formId === 'install'`: if `$envExists`, respond `403` ("Already
  installed.") - this is the "self-deletion": once `.env` exists the route
  is permanently inert, no code or file is ever removed from disk. (See
  "Why not delete a file" below.)
- Else if `!$envExists` and `$formId` is neither `install` nor `health`:
  `302` redirect to `/install`. This means visiting the homepage, `/admin`,
  or any form endpoint on a fresh clone with no `.env` lands you on the
  installer automatically. `/health` keeps working unconditionally (useful
  for container/orchestrator health checks pre-install).

**New `formflow\Install\InstallController`** (mirrors `AdminController`'s
`handle()`/`render()` shape):

- `GET /install`: renders the wizard form.
- `POST /install`: validates input, writes `.env`, redirects to
  `/admin/login`.

**Form fields → `.env` keys**:

| Field | Env key | Notes |
|---|---|---|
| App URL | `APP_URL` | required |
| SMTP DSN | `MAILER_DSN` | required, e.g. `smtp://user:pass@host:587` |
| From address | `MAIL_FROM` | required |
| From name | `MAIL_FROM_NAME` | default `formflow` |
| Turnstile secret | `TURNSTILE_SECRET` | optional - blank is allowed, installer notes that any form with `'turnstile' => true` will then fail Turnstile checks until a real secret is set |
| Admin username | `ADMIN_USERNAME` | required |
| Admin password | *(not stored raw)* | required, min 8 chars, hashed with `password_hash()` into `ADMIN_PASSWORD_HASH` |

Not prompted, fixed/generated by the installer itself:
`APP_ENV=production`, `DATABASE_PATH=storage/submissions.sqlite`,
`IP_HASH_SECRET` = `bin2hex(random_bytes(32))`.

**Writing `.env`**: every value is wrapped in single quotes. This is a
direct consequence of the bug fixed earlier this session - Symfony Dotenv
interpolates unescaped `$...` sequences (which bcrypt hashes and some SMTP
passwords contain), corrupting them on every subsequent load unless
single-quoted. Symfony Dotenv's single-quoted values are raw/literal with
no escape sequences, so as a simple, safe rule: if any submitted field
contains a single-quote character, the installer rejects the submission
with a validation error asking the user to remove it, rather than
implementing quote-escaping.

**After writing `.env`**: also append the installer's own request IP to
`config/admin.php['allowed_ips']` (a plain, deterministic PHP array file)
so the operator isn't immediately locked out of `/admin/login` - this was
exactly the friction encountered while testing the API-key feature earlier
today. Then redirect to `/admin/login`.

**Why not delete a file**: there's no separate `install.php` file in this
app - the installer is a routed branch inside the single front controller,
same as `admin` or `health`. There's nothing to `unlink()`. More
importantly, having the web server process delete/rewrite its own PHP
source is a meaningfully worse security posture than the "refuse once
`.env` exists" gate: it would require the PHP-FPM/web user to have write
access to the application's code directory, whereas this design only ever
needs it to write `.env` (and rewrite `config/admin.php`) - the properties
the user actually wants (installer cannot be run twice, no lingering setup
UI in production) are fully achieved without that.

**Accepted risk**: like most self-hosted installers (WordPress's
`wp-admin/setup-config.php` included), there's a window between deploy and
the operator's first visit to `/install` during which anyone who reaches
the server first could complete setup with their own credentials. This is
standard for single-operator self-hosted software and out of scope to
close for v1 (no setup token, no CLI-only requirement).

**Filesystem note**: unlike the rest of the app (which only requires
`storage/` to be writable), the installer needs the project root and
`config/` writable during first install. Rather than documenting this as
a manual pre-check in the README, `InstallController::handle()` verifies
writability itself before rendering the form (checking the target file if
it already exists, its containing directory otherwise) and, on failure,
renders a `503` page listing the exact unwritable path(s) instead of
failing later with a raw `file_put_contents` warning. This keeps the
operational requirement self-diagnosing rather than something the README
has to explain up front.

## 3. Shared light/utilitarian design

**New static asset**: `public/assets/style.css` - served directly by the
webserver/dev server as a real file (no front-controller routing needed;
confirmed this works with the documented Nginx `try_files`, Apache
`RewriteCond ... !-f`, and the PHP built-in dev server, all of which serve
existing files before falling back to `index.php`).

Content: CSS custom properties for a light theme by default, overridden
under `@media (prefers-color-scheme: dark)`; system sans-serif font stack
(dropping the homepage's current monospace/dark look, per the "not a black
page" feedback); a max-width container, a simple top nav bar, basic table
styling (borders, padding, header row background), form/button/input
styling, and an error/success banner style reused by login and the
API-keys/whitelist forms.

**Admin layout refactor**: `AdminController::render()` currently does
`extract(); ob_start(); require "views/$view.php"; return ob_get_clean();`
with each of the 5 view files independently duplicating
`<!DOCTYPE html><html><head>...` boilerplate and its own nav links. This
gets split into:

- Each view file (`dashboard`, `submission`, `whitelist`, `api-keys`,
  `login`) shrinks to just its body content (heading + form/table markup),
  no `<html>`/`<head>`/`<body>` wrapper, no repeated nav links.
- `render()` wraps that body in one shared shell that includes the CSS
  link, `<title>`, and - for every page except `login` - a nav bar
  (Submissions | API keys | IP whitelist | Log out).
- The `login` page renders without the nav bar (nothing to navigate to
  pre-auth), as a centered simple card.

**Homepage**: same stylesheet link, restyled to the light/utilitarian
look, content unchanged (description, feature list, links).

**Install wizard**: uses the same shared stylesheet, simple form layout,
no nav bar (pre-auth, one-time use).

No JavaScript is introduced anywhere in this design.

## Testing

- `AdminControllerTest`: dev-login bypass succeeds when whitelisted +
  loopback; fails (falls through to normal invalid-credentials handling)
  when whitelisted but not loopback (simulated via a non-loopback
  `REMOTE_ADDR` that's still in the configured whitelist, isolating the
  loopback check from the IP-whitelist gate).
- New `InstallControllerTest`: GET renders the form; POST with valid data
  writes a `.env` file (in a temp directory) with correctly single-quoted
  values and a verifiable `password_hash`; POST with a value containing a
  single quote is rejected; a second GET/POST after `.env` exists returns
  403; `config/admin.php` gets the requester's IP appended.
- Existing `AdminControllerTest` assertions on rendered body content
  (`'<form'`, `'contact'`, `'Ada'`, etc.) continue to pass unchanged since
  the refactor only wraps existing content, it doesn't remove any of it.
